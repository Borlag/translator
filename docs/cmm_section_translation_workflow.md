# Workflow перевода частей одного CMM

Этот workflow нужен для последовательного перевода частей одного и того же документа так, чтобы:

- терминология была общей для всех частей;
- найденные исправления не терялись между запусками;
- форматирование проверялось одинаково для каждого нового файла;
- glossary и основной prompt были привязаны к одному и тому же пайплайну.

## 1. Источники контекста

Для всех частей одного документа используем одни и те же исходные материалы:

- глоссарий: `for_test/new_formating/glossary.md`
- основной prompt: `for_test/new_formating/general_prompt.md`

Пути к этим файлам также записываются в JSON-отчет перевода, чтобы у каждого результата была явная привязка к одному и тому же контексту.

## 2. Общая база правил

Общая rulebase хранится в `scripts/manual_translate_part1.py`, а общий запуск делается через `scripts/translate_cmm_section.py`.

В shared rulebase добавляем:

- новые точные соответствия;
- правила для повторяющихся заголовков, таблиц и колонтитулов;
- нормализацию дат, диапазонов страниц и сервисных подписей;
- устойчивые исправления форматирования, которые должны применяться ко всем следующим частям;
- постобработку таблиц, которая после layout auto-fix:
  поднимает шрифт в ячейках минимум до `9 pt`,
  убирает лишние интервалы,
  сохраняет читаемость без выхода текста за границы.

Если найден новый устойчивый паттерн, его нужно добавлять именно в shared rulebase, а не в отдельный одноразовый скрипт под конкретную часть.

## 3. Перевод следующей части

Команда:

```powershell
python scripts/translate_cmm_section.py `
  --source "C:\path\to\partX.docx" `
  --output "C:\path\to\partX_ru_v1.docx" `
  --report "C:\path\to\partX_ru_v1.report.json"
```

Рекомендация по именованию:

- рабочая версия: `*_ru_v1.docx`, `*_ru_v2.docx`, `*_ru_v3.docx`
- после проверки и утверждения: обновить канонический `*_ru.docx`

Это полезно, потому что файл нередко открыт в Word, и прямое перезаписывание бывает заблокировано.

## 4. Обязательная проверка после перевода

Команда:

```powershell
python scripts/review_cmm_translation.py `
  --docx "C:\path\to\partX_ru_v1.docx" `
  --render-dir "C:\path\to\tmp\partX_ru_v1_render" `
  --report "C:\path\to\tmp\partX_ru_v1_review.json"
```

Проверка делает две вещи:

- ищет остаточный английский в самом DOCX;
- рендерит DOCX через Word и проверяет уже PDF-представление страниц.

Review-скрипт считает шумом буквенные суффиксы и референсы вроде `A)`, `P.(31)`, `(c)AC12221`, но продолжает ловить реальные остатки английских слов, в том числе в таблицах, оглавлении и списке рисунков.

## 5. Что считаем допустимым остатком

Не переводим:

- каталожные и сервисные коды вроде `A320-32-1374`;
- буквенно-цифровые reference IDs;
- официальные названия компаний и URL, если их нужно сохранить как собственные имена.

Переводим:

- служебные подписи и колонтитулы;
- даты и диапазоны страниц;
- заголовки таблиц и элементов оглавления;
- повторы в содержании, списке рисунков и перечнях страниц;
- любые обычные английские слова в ячейках таблиц.

## 6. Зафиксированные решения по оформлению

Для единообразия между частями:

- даты вида `Mar 18/2025` приводим к формату `18.03.2025`;
- диапазоны `601 to 603` приводим к `601-603`;
- перечисления `601 and 602` приводим к `601, 602`;
- колонтитулы `Page` и `No.` переводим в `Стр.` и `№`;
- если русский текст расширяется, применяем общий auto-fix верстки перед финальной проверкой;
- для таблиц после auto-fix обязательно проверяем, что итоговый шрифт не опускается ниже `9 pt`.

## 7. Как поддерживать согласованность между частями

Для каждой новой части:

1. сначала запускаем `translate_cmm_section.py`;
2. потом запускаем `review_cmm_translation.py`;
3. если найден новый повторяемый паттерн, правим shared rulebase;
4. после правки перегенерируем текущую часть;
5. если правило влияет на уже переведенные части, по необходимости перепрогоняем и их.

Так все части остаются согласованными и используют один и тот же накопленный набор решений.

## 8. Embedded Figure OCR Pass

Если DOCX-review уже чистый, но на визуальном рендере остаются английские слова внутри встроенных figure/image-объектов:

1. делаем дополнительный OCR/визуальный проход по PNG-страницам рендера;
2. находим конкретный `word/media/*` asset или drawing/textbox XML, откуда пришёл остаток;
3. патчим сам media asset или XML;
4. сохраняем отдельный manual-fix JSON и повторяем `render + review`.
